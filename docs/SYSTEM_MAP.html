01 — Orientation

The whole system

Three ways in, one engine, one graph store, four ways out. Everything else in this document is detail hanging off that shape.

The engine's single job is to turn prose into a queryable graph. It does not try to be an editor — Notion is better at that — and it does not try to be a chat product. It reads notes from wherever they come from, extracts facts, works out which names refer to the same thing, builds a graph, and exposes that graph to whatever asks.

The thing most people get wrong first

The documented design says Notion is the content layer. In practice 51 of 55 notes arrive through MCP, not Notion — the dominant author is an AI agent, not a person typing. The architecture below reflects the system you actually have, not the one the original README described.

Live drift, right now

SQLite says 55 notes and 633 triples; Neo4j says 54 and 623. Both numbers are correct. The pipeline writes only to the backend currently selected, so the copy you are not using falls behind until you re-migrate. The 10-triple gap is different: SQLite has no uniqueness constraint on raw_triples, so a fact the extractor emitted twice from one note is stored twice, while Neo4j's MERGE collapses it. Neo4j's number is the more correct one.

03 — Walkthrough

One note, start to finish

Follow a single sentence — “Sarah reports to Mei.” — from the moment it is written to the moment the graph can answer a question about it.

  1. STAGE 0

    Sync — pull prose in from Notion

    Detects whether the configured id is a database or a bare page, then reads every row. Blocks are flattened to plain text, Brahmastra's own insight toggle is stripped out, and empty pages are skipped. Change detection compares content, not Notion's last_edited, because write-back bumps that timestamp without the body actually changing.

    writes → notes (status pending only if content changed)
  2. STAGE 0b

    Drain checkpoints — recover conversations

    Session hooks queue raw transcripts to disk as JSON. This stage distils each into entity-rich prose and stores it as a note. It runs before extract so anything recovered is graphed in the same run. A queue file is deleted only once its note exists, so an LLM outage delays a checkpoint rather than losing it.

    reads → data/checkpoints/*.json  ·  writes → notes
  3. STAGE 1

    Extract — prose becomes facts

    Each pending note goes to the LLM in JSON mode with the ontology in the system prompt. Returned triples are validated: placeholders like “unknown” are rejected, and anything off-ontology is degraded to related_to rather than dropped. Silent dropping is why an earlier version left no Veraxion entity at all despite the sentence naming it.

    writes → raw_triples  ·  updates → notes.extraction_status
  4. STAGE 2

    Resolve — decide which names mean the same thing

    Three signals combine: exact match, Jaro-Winkler string distance, and cosine similarity over 384-dimension sentence-transformer embeddings. Union-Find merges the resulting pairs into clusters, and the longest, most complete spelling wins as the canonical name. This is the stage that makes “Sarah”, “sarah” and “Sarah K.” one node instead of three.

    writes → canonical_map, entity_clusters
  5. STAGE 3

    Build graph — structure and importance

    Triples are rewritten through the canonical map and loaded into NetworkX. PageRank scores importance, Louvain finds communities, functional relations are checked for contradictions (a person cannot be located_in two places), and unconnected-but-similar pairs become predicted links.

    writes → graph_cache  ·  on Neo4j also (:Entity) + typed edges
  6. STAGE 4

    Cluster summaries — name each community

    The 25 largest clusters get a one-sentence theme from the LLM, which is what makes global questions (“what is this whole graph about?”) answerable without reading every note. Fails soft: a cluster that errors keeps its members and loses only its label.

    merges into → graph_cache.stats
  7. STAGE 5

    Cache — one read for the whole graph

    The finished graph and its statistics are serialised so the API and the D3 front end can load everything in a single read instead of recomputing PageRank per request.

    writes → graph_cache (one row per workspace)
  8. STAGE 6

    Write back — return the intelligence to Notion

    Two jobs. First, notes marked publish that have no Notion page get one created, and the returned page id is persisted — without that, every run would create the page again. Second, each page receives a single 🧠 Brahmastra Insights toggle listing its relationships, contradictions and suggested links. The toggle is deleted and rewritten each run, so it stays current rather than accumulating.

    writes → Notion pages  ·  writes → notes.notion_page_id
Reading the result

A run returns status: ok | partial | error plus failed_stages[]. This matters more than it sounds: before it existed, a run where every single extraction failed still looked successful. Write-back is now skipped entirely when extraction failed for every note, rather than pushing a stale graph into Notion.

04 — Alternatives

Every swappable part

Six decisions are already pluggable. For each: what runs today, what else is available, and what actually changes if you switch.

Graph store

GRAPH_BACKEND
  • sqlite default One file, zero setup, no network. Search is lexical only — no vector similarity. Right for local work and tests.
  • neo4j Shared across machines. Native traversal, vector + BM25 hybrid search, real constraints. Required for deployment. Free tier suspends after ~3 days idle.

Adding a third means implementing one class against the GraphStore contract — roughly 104 call sites go through db.* and none touch a backend directly.

Language model

LLM_PROVIDER · GROQ_MODEL · OLLAMA_MODEL
  • groq default openai/gpt-oss-120b, ~0.8 s per call, 131k context. Free tier has a hard daily token cap. Must honour JSON mode — extraction depends on it.
  • ollama qwen2.5:7b-instruct locally. No quota, no network. On a 4 GB laptop GPU the model does not fit and spills to CPU: 1m37s–3m57s per call, roughly 100× slower.
  • anthropic Cloud fallback. Configured but not the default path.

Selection is cloud-first and automatic, so the same code deploys unchanged. An explicit provider only wins if it is actually reachable — a stale ollama setting with a dead server falls through instead of failing the run.

Where notes come from

NOTION_DATABASE_ID · per-workspace override
  • database mode active Each row of a Notion database is a note. Detected automatically.
  • page mode Every page the integration can see becomes a note. Friendlier if you keep notes as loose pages rather than a database.
  • no Notion at all Perfectly valid. MCP already supplies 51 of 55 notes; sync simply reports skipped.

Which graph you are working in

BRAHMASTRA_WORKSPACE
  • default active One graph holding everything. Existing data was migrated here, so single-graph use is unchanged.
  • named workspaces Separate graphs for personal, office, per-project. Uniqueness is per workspace — two workspaces may each hold a different “Sarah”, and merging them would corrupt both.

What reaches Notion

notes.publish
  • curated chosen Design records and decisions get a page; session checkpoints stay in the graph. Keeps a human workspace readable instead of filling it with agent transcripts.
  • everything Nothing is invisible, but ~50 pages appear at once and every future checkpoint adds more.
  • annotations only The original behaviour: annotate pages that already exist, never create any.

Retrieval strategy for /ask

POST /ask {"depth": 1..3}
  • local auto Pulls the subgraph around the entities named in the question. Depth 2 is selected automatically for chained questions such as “Sarah's manager's other reports”.
  • global Answers from cluster summaries instead of specific entities — for broad questions about the whole corpus.
05 — The subtle part

The two feedback loops

Writing into the same place you read from creates a cycle. There are two, they fail silently, and each needed its own guard.

A third cycle is worth naming because it is not guarded: publishing a note does not push later edits to that page. Publishing creates, and stops. Updating a page a human may have edited is a merge problem, not a write, and it was left alone deliberately.

06 — Yours to call

Open decisions

Five things the system currently does one way, where the other way is defensible and the choice is genuinely yours.

DecisionTodayThe case for changing
Which store is authoritative SQLite locally, Neo4j for deploy Running both means one always drifts. Committing to Neo4j everywhere removes a whole class of “which copy is right?” — at the cost of needing the network to work at all.
Provenance on triples None — a fact distilled by a 7B model is indistinguishable from one you wrote This is the largest structural gap. Marking origin would let /ask weight human notes above machine ones, and let contradiction detection prefer the human side.
Cluster summaries All 25 recomputed every run Most clusters are unchanged since yesterday. Caching by membership would cut this to near zero on a typical run.
Timeout retries A timeout is retried three times A timeout means the model cannot handle that input; retrying identically cannot help. This burned 12 of 45 minutes on one run.
Duplicate triples in SQLite No uniqueness constraint Neo4j already enforces it. Adding the same constraint to SQLite would make the two backends agree on counts.
Before deploying

Neo4j Aura's free tier suspends after roughly three days of inactivity, and while suspended its hostname stops resolving entirely — which looks exactly like the instance having been deleted. For anything long-lived this is an operational constraint, not a detail.
